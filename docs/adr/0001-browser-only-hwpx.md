# ADR 0001 — HWPX 처리를 브라우저에서 한다

- 상태: 채택
- 날짜: 2026-08-28

## 배경

`rhwp.co.kr`을 HWPX AI 문서 편집 서비스로 다시 만든다.
첫 마일스톤은 "업로드 → 분석 → 경량 미리보기"다.

HWPX 파싱을 어디서 할지 정해야 한다. 이 선택이 저장소, 개인정보, 비용,
운영 복잡도를 한꺼번에 결정한다.

## 검토한 선택지

### A. 브라우저에서 전부 처리

파일 선택 → 브라우저에서 ZIP 해제 → XML 파싱 → 미리보기.
나중에 AI를 붙일 때도 **파일이 아니라 문서 텍스트 일부만** Worker로 보낸다.

- 성능: 네트워크 왕복이 없다. 실측 4.83MB 문서가 브라우저에서 9.2ms.
- 구현 난이도: ZIP/XML을 직접 다뤄야 한다. 다만 표준 API(`DecompressionStream`)로 충분했다.
- 개인정보: 파일이 기기를 벗어나지 않는다. 사내 문서를 다루는 서비스에서 가장 큰 장점.
- 비용: 서버 CPU/대역폭/저장소 비용이 0.
- 운영: 저장소·DB·업로드 정리 배치·보존기간 정책이 전부 불필요.

### B. Cloudflare Worker에서 파싱

파일을 업로드 → Worker가 파싱 → 문서 모델을 브라우저로 반환.

- 성능: 10MB 업로드 왕복이 파싱보다 훨씬 오래 걸린다. Worker CPU 시간 제한도 걸린다.
- 구현 난이도: 파싱 코드 자체는 같다. 대신 업로드 엔드포인트, 크기 제한,
  임시 저장, 에러 처리, 요청당 메모리 관리가 추가된다.
- 개인정보: 사내 문서가 서버를 거친다. 보존하지 않더라도 "거친다"는 사실 자체를
  설명하고 방침에 명시해야 한다.
- 비용: 요청·CPU·대역폭 과금.
- 운영: 남는 파일 정리, 남용 방지, 용량 제한 등 운영 표면이 늘어난다.

## 결정

**A를 선택한다.**

결정적인 이유는 두 가지다.

1. **개인정보.** 대상이 사내 문서다. "서버에 올라가지 않는다"는 것이
   기능 하나보다 큰 제품 가치다. B는 이걸 포기하면서 얻는 게 없다.
2. **patch engine의 요구사항과 맞는다.** 결과 HWPX는 원본 파일의 나머지
   바이트를 그대로 유지해야 한다. 원본 `ArrayBuffer`를 브라우저에 그대로
   들고 있는 편이 서버로 왕복시키는 것보다 단순하고 안전하다.

성능도 A가 낫지만, 그건 부수적이다. B가 필요한 유일한 상황은 브라우저가
감당 못 할 만큼 무거운 처리인데, 실측상 그렇지 않다.

## 결과

- 서버 파일 저장소, S3, DB가 필요 없다.
- Worker는 나중에 **AI 프록시 용도로만** 쓴다. OpenAI 키를 프론트엔드
  번들에 넣지 않기 위해서다. Worker는 문서 텍스트를 받아 Edit Plan을 돌려줄 뿐,
  HWPX 파일을 다루지 않는다.
- 브라우저가 `DecompressionStream`을 지원해야 한다(2023년 이후 주요 브라우저).
  미지원 브라우저에는 명확한 안내 메시지를 낸다.

## 부수 결정

### 의존성을 추가하지 않았다

- **ZIP**: `fflate`/`jszip` 대신 직접 구현(약 200줄). 이유는 재패키징 때
  엔트리 순서·항목별 압축 방식·타임스탬프를 원본 그대로 재현해야 하는데,
  그 제어를 라이브러리 뒤에 두고 싶지 않았다. 압축 해제는 표준
  `DecompressionStream('deflate-raw')`을 쓴다.
- **XML**: `DOMParser` 대신 바이트 오프셋을 추적하는 스캐너를 직접 구현.
  DOM으로 파싱해 다시 직렬화하면 "원본 바이트 보존"이 깨진다. 게다가
  Node(테스트)와 브라우저에서 같은 코드가 돌아야 한다.

두 결정 모두 "미래 확장을 위한 추상화"가 아니라 **이번 마일스톤과 다음
마일스톤이 실제로 요구하는 제약**에서 나왔다.
