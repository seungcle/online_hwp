# 로드맵

## 지금 (마일스톤 1) — 완료

HWPX 업로드 → 구조 분석 → 경량 미리보기.
단계별 처리 시간 측정. AI 패널은 자리만.

## 다음 (마일스톤 2) — AI 수정 계획

```text
자연어 요청
  → Cloudflare Worker (OpenAI 프록시)
  → 검증된 Edit Plan (JSON)
  → 브라우저의 결정적 patch engine
  → 새 HWPX 내려받기
```

### 붙이는 순서

1. **patch engine 먼저.** AI 없이, 손으로 만든 Edit Plan으로 결과 HWPX를
   생성하고 한글에서 열리는지 검증한다. 필요한 것은 이미 모델에 다 있다.
   문단마다 텍스트 조각의 바이트 구간(`TextFragment`)을 들고 있으므로,
   바뀌는 구간만 새 바이트로 교체하면 된다. ZIP 재패키징은 엔트리 순서와
   항목별 압축 방식을 원본 그대로 재현해야 한다(`ZipEntry`가 그 정보를 보존한다).
2. **Edit Plan 스키마 확정.** 최소한으로 시작한다.
   ```json
   { "operations": [
     { "type": "replace_text", "paragraphId": "s0-p12",
       "oldText": "2025년 사업 제안서", "newText": "AI 교육 사업 제안서" }
   ]}
   ```
   `oldText`를 반드시 넣고, 적용 전에 현재 문단 텍스트와 일치하는지 확인한다.
   불일치하면 적용하지 않고 사용자에게 알린다. AI가 엉뚱한 문단을 짚었을 때
   조용히 망가지는 것을 막는 안전장치다.
3. **Worker 프록시.** OpenAI 키는 Worker의 secret으로만 둔다. 프론트엔드
   번들에 키가 들어가는 일은 없어야 한다. structured output / tool calling으로
   스키마를 강제하고, Worker에서 한 번 더 검증한 뒤 브라우저로 돌려준다.
4. **보내는 데이터 최소화.** HWPX 파일은 보내지 않는다. 문단 id와 텍스트만
   추린 표현을 보낸다. 개인정보처리방침에 전송 범위를 명시한 뒤에 켠다.
5. **변경 미리보기.** 적용 전에 어느 문단이 어떻게 바뀌는지 보여주고,
   사용자가 승인해야 파일이 만들어지게 한다.

## 그 다음 — 지원 범위 넓히기

실제 양식을 처리하면서 새로운 HWPX 패턴이 나올 때마다 최소한으로 대응하고,
그 양식을 회귀 테스트 fixture로 남긴다.

```text
실제 양식 추가 → 새 패턴 발견 → 최소 기능 추가
  → 해당 양식을 fixture로 저장 → 기존 양식 전체 재검증
```

아직 확인하지 못한 영역: 머리말·꼬리말, 각주, 메모, 글상자 안의 텍스트,
차트·수식이 본문에 섞인 경우.

## 나중 — 알려진 양식의 기계적 처리 (지금 만들지 않는다)

같은 양식을 반복해서 쓰는 조직이 많다. 한 번 처리해 본 양식은
어느 문단이 어떤 필드인지 이미 알고 있으므로 AI 판단 없이 채울 수 있다.

```text
등록된 사내 양식 (출장보고서 등)
  → 저장해 둔 field map
  → AI 없이 결정적으로 채움 (빠르고, 비용 0, 결과가 항상 같음)

처음 보는 HWPX
  → 구조 분석 → AI 판단
```

**이번 구현에서는 만들지 않는다.** 여기 기록만 남긴다.
먼저 확인해야 할 것은 "실제 사내 양식 대부분이 텍스트 치환만으로 처리되는가"이고,
그 답이 나오기 전에 양식 등록 UI나 저장소를 만드는 건 이르다.
필드 맵을 어디에 둘지(브라우저 로컬 저장 / 내보낼 수 있는 JSON 파일 /
서버 저장)도 그때 정한다. 저장소를 도입하는 순간 지금의 "서버에 아무것도
남지 않는다"는 성질이 깨지므로 신중해야 한다.
